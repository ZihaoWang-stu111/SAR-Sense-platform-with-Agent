# RAG 引用证据抽屉设计

## 1. 目标

当前回答中的 `[1]`、`[2]` 只是视觉标号，参考来源还直接展示内部 `chunk_id`。用户能知道引用来自哪个文件，却不能方便地核对该引用对应的原始证据。

本次改造只解决一个问题：让用户点击回答引用或来源条目后，在聊天页右侧查看对应父块全文。

成功标准：

- 回答中的引用编号可以点击。
- 参考来源不再显示内部 `chunk_id`，改为文件名、页码和相关度。
- 点击引用编号或来源条目时，打开同一个右侧证据抽屉。
- 抽屉展示完整父块正文，并允许独立滚动。
- 每次读取证据都由后端重新校验当前用户权限。

## 2. 方案选择

采用“按需读取父块”的轻量方案：

1. RAG 回答继续输出来源编号与父块 ID，父块 ID 只作为前端请求参数，不展示给用户。
2. 用户点击引用后，前端调用受保护的证据接口。
3. 接口从现有 `parent_chunks` 表读取父块，再根据父块的 `doc_id` 校验文档 ACL。
4. 校验通过后返回父块正文和面向用户的来源信息。

不把父块全文直接塞进聊天消息，也不从 Chroma 再查一次。这样不会扩大会话记录，不增加数据库表，也不会改变在线检索流程。

## 3. 前端交互

### 3.1 引用与来源

- 回答正文中的 `[n]` 改为可访问的行内按钮，视觉样式保持现状。
- 参考来源中的每一条改为可点击行。
- 来源行展示：文件名、页码（存在时）、相关度和“查看证据”。
- `chunk_id`/`parent_id` 只保留在 DOM 的 `data-parent-id` 中，不显示在界面上。

### 3.2 右侧抽屉

抽屉包含：

- 文件名。
- 页码和相关度。
- 完整父块正文。
- “查看原文件”操作。
- 关闭按钮。

抽屉打开后正文区域独立滚动；点击遮罩、关闭按钮或按 `Esc` 均可关闭。移动端使用接近全屏宽度，避免正文被挤成窄列。

接口请求期间显示加载状态；不存在、权限不足和文档已失效统一显示“证据不存在或当前无权访问”，不泄露资源是否真实存在。

## 4. 数据协议

### 4.1 RAG 来源文本

新生成的来源增加可选页码：

```text
[1] SFQ-Det.pdf | chunk_id=<parent_id> | page=3 | score=0.9950
```

没有页码时省略 `page`。前端解析器同时兼容旧格式：

```text
[1] SFQ-Det.pdf | chunk_id=<parent_id> | score=0.9950
```

这里继续使用现有 `chunk_id` 字段名，以兼容已经落库的历史 RAG 结果；它当前实际指向父块 ID。UI 和新接口内部统一按 `parent_id` 理解，不做历史数据迁移。

### 4.2 证据接口

新增：

```http
GET /api/knowledge/evidence/{parent_id}
Authorization: Bearer <token>
```

成功响应：

```json
{
  "filename": "SFQ-Det.pdf",
  "page": 3,
  "content": "父块完整正文……",
  "doc_id": "985419bb186328d7",
  "download_url": "/api/knowledge/files/985419bb186328d7/download"
}
```

`page` 和 `download_url` 可以为空。响应不返回内部父块 ID，前端已经持有本次请求对应的 ID。

## 5. 权限与安全

一次点击是一次新的 HTTP 请求，不能依赖检索发生时的权限判断。原因包括：

- 用户角色可能在回答生成后被管理员调整。
- 文档 ACL 可能改变，文档也可能已被删除或停用。
- `parent_id` 是资源标识，不是访问凭证；其他用户可能从日志、历史消息或共享截图中得到它。

后端处理顺序：

1. JWT 鉴权，获得数据库中的当前用户和实时角色。
2. 读取父块，但在权限判断前不向客户端返回任何父块信息。
3. 从父块 metadata 取得 `doc_id`。
4. 查询文档 ACL，要求文档为 `active`，并确认用户是 admin 或角色位于 `allowed_roles`。
5. 通过后才返回正文；父块不存在、文档不存在、文档失效或无权限均返回 404。

这不是重复过滤检索结果，而是防止新读取接口产生 IDOR/BOLA 越权。

## 6. 代码边界

后端：

- `repositories/parent_chunk_repository.py`：复用现有 `get(parent_id)`，不新增 Repository 方法。
- `crud/knowledge_acl.py`：复用现有文档 ACL 查询逻辑。
- `schemas/knowledge.py`：新增证据响应模型。
- `api/routers/knowledge.py`：新增证据读取接口；同步父块查询放入线程池，避免阻塞 FastAPI 事件循环。
- `rag/rag_service.py`：在新来源行中追加可选页码。

前端：

- `templates/chat.html`：增加一个原生 `dialog` 右侧抽屉，遮罩由浏览器的 `::backdrop` 提供。
- `js/chat.js`：兼容新旧来源格式；使用事件委托处理引用编号和来源行点击；通过现有 `apiFetch()` 请求证据。
- 聊天页现有样式文件：增加抽屉、加载态、来源按钮和移动端样式。

父块正文使用 `textContent` 写入页面，不把数据库内容拼接为 HTML，避免持久化 XSS。

## 7. 异常与边界

- 旧历史来源没有页码：仍可点击，来源列表只省略页码。
- 来源行格式不完整：继续按普通文本展示，不创建不可用的点击入口。
- 父块已被旧版本清理：接口返回统一 404，聊天历史本身仍可正常显示。
- 用户连续点击不同引用：后一次请求成为当前抽屉内容；不使用长期客户端缓存，确保权限变更后再次点击会重新鉴权。
- 未登录或 token 过期：沿用 `apiFetch()` 的现有 401 处理。

## 8. 测试与验收

后端：

- admin 可以读取任意 active 文档的父块。
- 普通用户只能读取 `allowed_roles` 包含其当前角色的文档父块。
- 无权限、父块不存在、文档不存在和非 active 文档统一返回 404。
- 接口返回完整父块正文，不查询 Chroma。

前端：

- 新旧两种来源格式都能正确折叠和渲染。
- 点击回答中的 `[n]` 与点击对应来源行打开同一证据。
- 页面不显示内部父块 ID。
- 加载、失败、关闭和移动端状态正常。
- 父块中的 HTML 字符串按纯文本显示，不被浏览器执行。

手工回归：

1. 用有权限的普通用户完成一次 RAG 问答并打开引用证据。
2. admin 撤销该角色的文档权限。
3. 普通用户再次点击同一历史引用，接口返回 404，抽屉显示统一错误。
4. admin 仍能打开该证据并访问原文件。

## 9. 明确不做

- 不新增数据库表或迁移脚本。
- 不修改 Chroma、BM25、重排或父块回表算法。
- 不调用额外 LLM。
- 不做句子级高亮或 PDF 页内定位。
- 不把父块全文复制进会话消息。
- 不为证据抽屉另建前端框架或状态库。
